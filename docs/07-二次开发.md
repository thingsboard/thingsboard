# 7  二次开发设计

> *中铁信科物联网平台文档集 ｜ 第 7 章* ｜ [总目录](../README.md) ｜ [设计说明书总览](02-总体设计.md) ｜ 上一章 [数字孪生与数据加工](06-数字孪生与数据加工.md) ｜ 下一章 [非功能设计](08-非功能设计.md)

分工先定清楚：**ThingsBoard 后端一行不改**（升级跟着官方 LTS 走），只改它的前端（新增页面与菜单）；**新增能力放进两个自研服务**：面向请求的 platform-service 与面向吞吐的 ingest-worker。定制前端只调用 platform-service，不直连 ThingsBoard；TB 的凭证只在后端持有。

这样切分的好处是：底座可随时升级、出问题可回退；新功能迭代不进 TB 的代码库；前端与后端各自独立发布。

## 7.1  四个可部署单元

**表 7-1  部署单元划分**

| 单元 | 内容 | 部署方式 | 升级影响 |
| --- | --- | --- | --- |
| ThingsBoard | 官方镜像/发行包，不加插件、不改源码 | 官方部署形态 | 按 LTS 升级，回归后端调用点 |
| platform-service | 自研 Spring Boot 服务（模块见 7.3），面向请求 | 独立部署，≥2 副本 | 独立发版 |
| ingest-worker | 自研 Spring Boot 服务，面向吞吐：消费 Kafka 遥测/事件并写 TDengine 与事件表 | 独立部署，3 副本起，按分区扩 | 独立发版，滚动重启不丢位点 |
| 定制前端 | TB UI（`ui-ngx`）定制构建后的静态资源 + 自研页面 | Nginx 静态托管，替换 TB 自带 UI | 与 TB 版本对齐，合并 UI 差异 |

四个单元之间只有三种连接：前端 → platform-service（HTTPS/JSON）；platform-service → ThingsBoard（REST）；ingest-worker ← Kafka，→ TDengine/PostgreSQL。API 与消费者不共享进程、不共享连接池，扩缩容与故障域彼此独立。

## 7.2  前端只改前端

**改什么。** 在 TB 的 Angular 前端（`ui-ngx`）里新增一个一级菜单“物联网平台”，下挂物模型管理、设备台账、项目/工点、事件中心、运维看板五个页面；其余设备、仪表板等页面沿用 TB 原生。所有新页面调 platform-service 的 `/api/*`，不调 TB 的 `/api/*`。

**怎么组织代码。** 把定制代码集中在 `src/app/modules/crec-iot/` 一个目录，路由懒加载，样式用独立前缀；这样 TB 升级时只需合并这一个目录的差异，冲突可控。

**登录与会话。** 前端提交账号密码到 platform-service `/api/auth/login`，后端调用 TB `/api/auth/login` 校验并拿到 JWT，换发平台自己的会话 token 返回前端；TB 的 JWT 加密保存在后端会话里，浏览器不持有。厂商管理员仍需直接使用 TB 原生页面时，单独走 TB 登录，两条会话互不影响。

**替代方案。** 团队不熟 Angular 时，可做独立前端（Vue3/React）并用 iframe 嵌入 TB 仪表板；代价是登录态与主题要额外对齐，只建议在定制页面很多时采用。

**不能碰的。** 不改 TB 的 REST 契约与数据库；不在前端直连 TB 的 `/api`（否则租户凭证会散落在浏览器）；不重写 TB 的登录页（保留厂商自助入口）。

## 7.3  platform-service 的模块划分

按包分模块；`tsl`/`registry`/`device`/`event`/`openapi`/`admin`/`bff` 仍在 platform-service 进程内，**`ingest` 已拆为独立服务 `ingest-worker`**，因为它按 Kafka 分区扩缩容、按吞吐扩容，与请求型 API 的生命周期不同。

**表 7-2  platform-service 模块**

| 模块 | 核心职责 | 主要依赖 |
| --- | --- | --- |
| tsl | TSL 注册、结构/业务校验、版本发布、模板生成与同步 | PG（`plat_tsl_*`）+ TB `/api/deviceProfile` |
| registry | 组织树、项目/标段、工点、设备—工点绑定与变更历史 | PG（`plat_org/site/binding`） |
| device | 设备开通、凭证生成与重置、批量导入、RPC 代理 | TB `/api/device`、`/api/rpc` |
| ingest-worker（独立服务） | 消费 Kafka 遥测/事件，按物模型建表加列并批量写 TDengine；事件写 `plat_event` | Kafka + TDengine + PG |
| metrics | 工点/项目/厂商维度指标计算与查询 | TDengine + PG（台账维度） |
| event | 事件中心：解析遥测事件与平台判定事件、去重、通知、处置回写 | Kafka + PG（`plat_event`） |
| openapi | 对外开放 API、WebSocket 推送、AK/SK 鉴权与限流 | 以上模块 |
| admin | 厂商租户开通/停用、平台用户与权限、审计日志 | TB sysadmin API + PG |
| bff | 定制前端的聚合接口（首页卡片、菜单权限、字典） | 以上模块 |

模块之间只通过接口与事件通信，禁止跨模块直接读对方的表；`ingest-worker` 与 `metrics` 是全链路里唯一允许写 TDengine 的模块。

## 7.4  数据归属

**表 7-3  数据归属与访问方式**

| 数据 | 归属 | platform-service 的访问方式 |
| --- | --- | --- |
| 设备、资产、模板、最新值 | ThingsBoard（PG） | 只读 REST；写入走 TB API，不直连库 |
| TSL 定义与版本 | platform-service（PG `plat_tsl_*`） | 自有库读写 |
| 组织树、项目、工点、绑定关系 | platform-service（PG `plat_*`） | 自有库读写 |
| 遥测明细、降采样、指标 | TDengine | 由 `ingest-worker`/`metrics` 写入，其余模块只读 |
| 标准化消息 | Kafka | 消费；生产仅限规则链外发与平台内部事件 |
| 会话、限流计数 | Redis（可选） | 缓存 |

不要跨库 JOIN：TB 的实体 ID 与平台台账通过 `(tenant_id, device_id)` 关联，需要联表时用接口聚合或建只读视图（视图也只读、不改 TB 表结构）。

## 7.5  关键接口

**表 7-4  平台接口清单（前端与开放 API）**

| 接口 | 方法 | 说明 | 调用方 |
| --- | --- | --- | --- |
| /api/auth/login、/api/auth/me | POST / GET | 平台会话登录、当前用户与权限 | 前端 |
| /api/tsl/products | GET / POST | 产品与 TSL 列表、提交 | 前端 |
| /api/tsl/products/{pid}/validate | POST | 结构 + 业务校验，返回逐条问题 | 前端 |
| /api/tsl/products/{pid}/publish | POST | 发布版本，触发模板生成/同步 | 前端 |
| /api/registry/sites | GET / POST | 组织节点与工点维护 | 前端 |
| /api/registry/bindings | POST / DELETE | 设备—工点绑定/解绑，写历史 | 前端 |
| /api/devices/batch | POST | 按产品批量导入设备并生成凭证 | 前端 |
| /api/devices/{id}/rpc | POST | 指令下发（属性设置/行为调用） | 前端 / 开放 API |
| /api/metrics/sites/{code} | GET | 工点维度指标（在线率、事件数、均值） | 前端 / 开放 API |
| /api/events | GET / POST | 事件查询与处置（确认/关闭/备注） | 前端 |
| /open/v1/* | GET / POST | 对外数据与指令接口，AK/SK 鉴权 | 业务系统 |

开放 API 与内部接口分两套路由：`/open/v1` 走 AK/SK 或 OAuth2 客户端凭证，`/api` 走平台会话；内部接口不暴露到公网。

## 7.6  与底座的集成约定

- **身份**：platform-service 为每个厂商租户保存一个“服务账号”（租户管理员），token 加密存储、自动刷新；开通/停用租户用 sysadmin 账号。所有写入都以对应租户的服务账号执行，不绕过租户隔离。
- **调用限速**：TB 没有批量接口，批量建设备/同步模板按 5~10 QPS 串行，失败重试并记录差异；大批量任务走异步任务表 + 进度查询。
- **消息**：规则链把标准化遥测与事件外发到固定 topic（如 `iot.telemetry.normalized`、`iot.event.normalized`），platform-service 消费；不在 TB 里写业务逻辑。
- **模板同步**：platform-service 用 `tsl2tb` 的转换结果调用 TB API，按名称/描述做幂等判断，差异写同步日志。
- **规则链**：仍属 TB 侧配置，由 platform-service 提供“导入规则链 JSON”的能力（可选），但不修改 TB 的规则链引擎。

## 7.7  升级与兼容

底座锁定官方 LTS 版本。升级前在预发环境回归：设备接入、模板同步、设备开通、RPC、事件查询、定制前端页面。因为 TB 后端未改，升级风险主要在两处：REST 契约变化（平台后端适配）与 UI 结构变化（定制前端合并）。所有 `plat_` 表随版本做增量迁移，禁止手工改库。
