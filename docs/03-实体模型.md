# 3  实体模型设计

> *中铁信科物联网平台文档集 ｜ 第 3 章* ｜ [总目录](../README.md) ｜ [设计说明书总览](02-总体设计.md) ｜ 上一章 [总体设计](02-总体设计.md) ｜ 下一章 [物模型](04-物模型.md)

本章把规范中的“产品、设备、组织、物模型”落到 ThingsBoard 的实体与关系上。设计目标是：业务人员看到的是中铁的组织与设备，平台内部仍然是标准的 ThingsBoard 实体，从而既能表达业务语义，又能复用底座能力。

## 3.1  租户模型：一个超级管理员，厂商各自一租户

常见做法是“集团一个租户、子分公司作 Customer”，本项目不采用。设备的建设、上传与运维责任在硬件厂商，若把厂商塞进 Customer，厂商用户会与同一租户内的其他厂商共处，隔离弱、授权繁琐（设备要逐台分配给客户）。平台改为**租户边界 = 厂商**：每个厂商一个 Tenant，数据与用户都关在租户内；中铁侧只保留**一个超级管理员**（ThingsBoard System Administrator），不属于任何租户，负责开通厂商、下发模板与跨租户巡检。

**表 3-1  角色与权限**

| 角色 | 归属 | 关键权限 | 典型操作 |
| --- | --- | --- | --- |
| 超级管理员 | 平台，不属于任何租户（sysadmin） | 全部租户、模板、规则链、系统设置；租户不可见其存在 | 开通/停用厂商租户、跨租户巡检、全局配置 |
| 厂商管理员 | 厂商 Tenant（Tenant Admin） | 本租户用户、产品、设备、TSL 提交、事件、仪表板 | 导入 TSL、建设备、管理本厂用户 |
| 厂商操作员 | 厂商 Tenant（Tenant User） | 本租户设备查看与维护（按角色细分） | 处理事件、查看曲线 |
| 中铁业务用户 | 平台数据服务（不进入 TB 租户） | 仅授权项目/工点的汇聚数据 | 大屏、查询、订阅 |
| 平台后端服务 | 独立部署，按租户使用服务账号 | 跨租户只读 + 按租户写入 | 物模型、台账、汇聚、开放 API |

开通流程：超级管理员创建租户（命名 `vendor-<厂商编码>`）→ 创建厂商管理员 → 交付接入指引（域名、端口、三元组导入模板）→ 厂商自助完成产品与设备创建。停用厂商时禁用其用户与设备凭证，数据保留用于追溯。

隔离说明：ThingsBoard 的租户隔离是强隔离（实体、遥测、规则链均按租户），超级管理员与平台后端服务是唯一例外；后端服务按租户持有服务账号，读取走 ThingsBoard API 与 Kafka 标准化数据，不直连各租户数据库。

## 3.2  组织与资产：业务树在台账，设备在租户

中铁的组织（集团—子分公司—项目部—项目/标段—工点）属于业务主数据，不属于任何厂商，因此不能放进厂商租户。平台后端服务的**台账模块**维护组织树与项目/工点（`plat_org`、`plat_site`），并用“设备—工点绑定”把厂商租户里的 Device 挂到业务位置上，绑定键为 `(tenant_id, device_id)`。

绑定关系是跨租户的唯一连接点：一台设备同一时间只能绑定一个工点；变更保留历史（谁在何时改绑）；解绑不删除设备数据。台账对外提供按组织、项目、工点聚合的设备数、在线率与事件数，由后端服务的汇聚模块计算后写入指标表。

ThingsBoard 的 Relation 仍然保留，用于厂商租户内部的分组与拓扑（如网关与子设备、设备组），不承担跨租户业务语义。

**表 3-2  关系类型与使用范围**

| 关系类型 | 方向 | 语义 | 使用范围 |
| --- | --- | --- | --- |
| Contains | 父 → 子 | 组成 / 归属 | 厂商侧设备组、网关—子设备 |
| Manages | 组织 → 对象 | 管理责任 | 台账（组织节点 → 项目 / 工点） |
| Monitors | 资产 → 设备 | 监测 / 采集 | 厂商侧（设备组 → 设备） |
| LocatedIn | 设备 → 资产 | 安装位置 | 厂商侧可选 |
| Owns | 客户 → 资产 | 产权 / 使用权 | 当前不启用（无 Customer 层） |

台账字段与校验：工点编码、名称、经纬度、所属标段/项目、责任人；绑定接口校验设备存在、租户启用、工点有效、无重复绑定，并记录操作人。

## 3.3  设备与设备模板

**设备模板即产品。** 在厂商租户内，一个产品（ProductID）对应一个 Device Profile，模板由平台后端服务的生成器创建（厂商只提交 TSL，不允许手改模板），名称采用“产品中文名 + 产品型号”，如“北斗监测型高精度接收机 H3”；ProductID、CategoryId 写入模板描述并同步到平台产品表。模板中配置传输方式（MQTT）、默认规则链、处理队列与 provisioning 策略；离线判定不放模板，由平台事件中心统一做（见 6.3）。

**设备命名。** 规范要求“设备型号 + 序列号”、不超过 48 个字符、仅英文数字下划线，这与 ThingsBoard 对 Device.name 的限制完全一致，可直接使用 DeviceName 作为 name，将中文别名、厂商、安装位置写入 label 与服务端属性，兼顾机器可读与业务可读。

**表 3-3  设备凭证策略**

| 凭证方式 | 适用场景 | 规范对应 | 说明 |
| --- | --- | --- | --- |
| Access Token | 直连形态；厂商自研终端 | 密钥认证（简化） | 一机一密，TB 原生支持，接入最简单 |
| X.509 证书 | 高安全等级设备（车载、涉密场景） | 证书认证（设备级） | 需 CA 与证书生命周期管理 |
| MQTT Basic | 视频平台等固定账号系统 | — | 固定用户名口令，适合非“一机一密”对象 |

规范的密钥认证使用 `username = ProductID + DeviceName; sdkappid; connid; expiry`，`password = base64(HMAC_SHA1(rawKey, username)) + ";hmacsha1"`，属于动态签名，而社区版 Transport 只校验静态凭证，平台侧无法验证。**处理方式统一为：存量设备升级固件，改用 TB 的 Access Token / X.509 / MQTT Basic 凭证与 `v1/devices/me/*` 主题**，不再保留 HMAC 签名逻辑。这一点必须在厂商接入指引中写明：报文语义不变，但凭证与主题要换。

设备 provisioning 建议**关闭自动注册**，由厂商批量导入（CSV/JSON），平台校验 DeviceName 唯一性与命名规则后写入；这与腾讯云“先建产品、再建设备、最后下发三元组”的流程一致。

## 3.4  实体视图与数据开放

Entity View 是**租户内**的只读投影，用于厂商把部分设备字段开放给本厂其他系统或仪表板。它不能跨租户，因此业务方（项目部）不通过 Entity View 取数，而由**统一数据服务**返回 DTO（字段裁剪、脱敏、按工点授权）。控制类操作仍经开放 API 路由到真实设备（Entity View 不支持 RPC）。

## 3.5  业务对象到实体/台账的映射总表

**表 3-4  业务对象与 ThingsBoard 实体/台账的映射**

| 对象 | 承载位置 | 关键约定 |
| --- | --- | --- |
| 中国中铁（集团） | 平台超级管理员 + 台账组织根节点 | 单一 sysadmin，不占租户 |
| 硬件厂商 | Tenant | 一厂商一租户，命名 `vendor-<编码>` |
| 厂商管理员 / 操作员 | Tenant Admin / User | 厂商自建，平台不代管 |
| 子分公司 / 项目部 | 台账组织节点 | 平台维护，不映射 TB 实体 |
| 项目 / 线路、标段、工点 | 台账项目 / 工点 | 跨厂商共用，设备按绑定归属 |
| 产品（型号） | Device Profile（厂商租户内） | 一产品一模板 |
| 设备实例 | Device（厂商租户内） | name=DeviceName，label=中文别名 |
| 物模型 TSL | 平台 TSL 注册表 | 厂商提交、平台校验发布 |
| 设备证书 / 密钥 | Device 凭证 + 密钥库 | 密钥不落明文，接口返回掩码 |
| 设备—工点归属 | 台账绑定 `(tenant_id, device_id)` | 唯一绑定、变更留痕 |
| 对外共享 / 大屏 | 统一数据服务 | 只读 DTO、按工点授权 |
| 业务系统 | 外部系统 | 经开放 API / Kafka / WebSocket 集成 |

**为什么不在 TB 里建业务树。** 跨租户无法建立 Relation；把组织树放进某一厂商租户会破坏隔离；设备改绑、项目重组在台账中只是一条记录的变更，在 TB 中则是跨实体的关系迁移。因此“设备拓扑在租户内、业务组织在台账、指标在汇聚层”是三层分工。

## 3.6  与腾讯 IoT 的产品、设备、物模型对齐

中铁规范在主题、三元组与 TSL 上与腾讯云 IoT Hub（IoT Explorer / 物联网通信）同源，因此平台的接入语义按腾讯定义，存储语义按 ThingsBoard 定义。二者不是“二选一”，而是同一份数据的两套视图：设备按腾讯方式接入，平台内以 ThingsBoard 实体承载。

**概念对齐。** 腾讯的三个核心对象——产品、设备、物模型——分别落到设备模板、设备与平台侧 TSL 注册表。

**表 3-5  腾讯 IoT 概念与 ThingsBoard 实体对照**

| 腾讯 IoT 概念 | 含义 | 平台实现 | 说明 |
| --- | --- | --- | --- |
| 产品（ProductId / ProductKey） | 同一类设备的集合，定义认证方式、数据协议与物模型 | Device Profile + 平台产品表 | 一产品一模板；ProductId 唯一，写入模板描述 |
| 产品分类（CategoryId） | 腾讯控制台的产品分类 | 平台分组/标签 | 便于按行业筛选与统计 |
| 设备（DeviceName） | 产品下的实例，产品内唯一 | Device（name=DeviceName） | label 存中文别名、厂商、安装位置 |
| 设备密钥（DeviceSecret） | 设备级密钥，参与 HMAC 签名 | 密钥库（密文）+ Access Token / MQTT Basic | 不落明文，接口返回掩码 |
| 设备证书 | 高安全场景的 X.509 凭证 | ThingsBoard X.509（mTLS） | 证书生命周期由平台管理 |
| 物模型（TSL） | 属性、事件、行为的 JSON 定义 | 平台 TSL 注册表（product_tsl 等表） | 权威源；驱动模板与校验，不直接存进 ThingsBoard |
| 属性（r / rw） | 设备状态数据流 | 遥测键 | 上行一律遥测；rw 的写入走 RPC |
| 事件（info / alert / fault） | 设备上报的事件 | Telemetry 保留键 | `event_id`/`event_type`/`event_ts` 随遥测上报，平台落事件表 |
| 行为（action） | 平台调用设备 | 双向 RPC | actionId 作方法名，params 作入参 |
| 设备影子 | 缓存设备最新状态 | 服务端属性 + 共享属性 + 最新遥测 | 以属性体系模拟，读写走 `$shadow/operation` |
| 设备状态（在线/离线） | 心跳遥测与最后上报时间 | Telemetry 心跳 + ingest 判定 | 超时在平台生成区间事件，不用告警实体 |
| 规则引擎/数据转发 | 云端消息路由 | 规则链 + Kafka 外发 | 业务系统经 Kafka/WebSocket 消费 |
| Topic 类 | 设备的主题权限模板 | ACL 白名单 | 设备只能 pub 上行、sub 下行 |

**字段对齐。** 平台产品表与设备表的关键字段直接沿用腾讯命名，避免迁移期再做一次字段翻译。

**表 3-6  腾讯字段与平台字段对照**

| 腾讯字段 | 平台字段/位置 | 处理方式 |
| --- | --- | --- |
| ProductId | `product.product_id`、`Device Profile.description` | 全局唯一，创建后不可修改 |
| ProductKey（若启用） | `product.product_key` | 与 ProductId 等价的一类标识，迁移时保留 |
| CategoryId | `product.category_id` | 映射为平台标签 |
| DeviceName | `device.name` | 直接使用，长度≤48、仅英文数字下划线 |
| DeviceSecret | 密钥库 `credential_ref` | 密文存储，重置即失效 |
| TSL `version` | `product_tsl.version` | 参与兼容性判断 |
| 属性 `id` / `mode` | 遥测键 / 写入方式 | 键名保持原样；rw 映射为 RPC 方法 `set` |
| 事件 `type` | 平台事件级别 | info→仅记录；alert→MAJOR；fault→CRITICAL |
| 行为 `actionId` | RPC 方法名 | 与腾讯保持一致，便于两端复用代码 |
| 影子 `desired` / `reported` | 共享属性 / 服务端属性 | 下发写 shared，上报写 server |

**设备迁移。** 对存量腾讯设备，改造量被压缩到“接入地址 + 三元组导入”两项：

- 设备侧：升级固件，改用 TB 凭证与 `v1/devices/me/*` 主题；不提供网关代理路径，HMAC 签名逻辑随固件升级删除。
- 平台侧：按产品导入 TSL 与设备凭证，建立 Device Profile 与 Device；配置共享属性、OTA 资源与规则链。
- 验证项：设备上线、属性上报、控制下发、事件流、影子读写、OTA、远程配置、NTP 八项逐一回归，通过后关闭旧通道。

**并行期。** 迁移窗口内可让平台与腾讯云并存：设备侧可临时双发（同一固件同时连两端），业务系统先读平台再逐步切换。并行期以“同一设备只归属一个写入端”为原则，避免控制指令双发导致状态抖动。
