## 4.1  TSL 结构解析

规范 6.3 规定物模型以 JSON（TSL）描述，包含产品信息与属性、事件、行为三类功能元素。样例文件 `9HYN9PJNOY.json` 展示了典型结构：`version`、`profile`（ProductId、CategoryId）、`properties`、`events`、`actions`，其中每个属性由 `id`、`name`、`desc`、`mode`、`required` 与 `define` 组成。

**表 4-1  TSL 结构及平台处理方式**

| TSL 字段 | 含义 | 平台处理 |
| --- | --- | --- |
| version | 物模型版本，如 1.0 | 作为发布版本号的一部分，参与兼容性判断 |
| profile.ProductId | 产品唯一标识 | 写入产品表与设备模板描述 |
| profile.CategoryId | 产品分类 | 映射为平台分组/标签，用于筛选与统计 |
| properties[].id | 属性标识符（遥测键） | 直接作为 ThingsBoard 遥测键，保持原样不改写 |
| properties[].mode | r 只读 / rw 读写 | 上行都是遥测；rw 额外提供 `set` RPC |
| properties[].define.type | 数据类型（bool/int/float/string/enum/timestamp/struct 等） | 按附录 A 映射为 boolean/long/double/string/json |
| properties[].define.min/max/step/unit | 取值范围、步长、单位 | 作为元数据入库，供校验与前端展示 |
| events[].type | info / alert / fault | 三类都走遥测保留键；alert/fault 由平台标记级别 |
| actions[] | 输入/输出参数定义 | 生成 RPC 方法模板 |

需要特别说明两点。其一是**类型系统不完全对齐**：规范的 `int` 为 32 位量级，ThingsBoard 以 `long` 存储，映射时需关注取值范围；`struct` 在规范中不允许嵌套，而 ThingsBoard 的 JSON 值可嵌套，平台应主动限制为单层并给出提示。其二是**时间戳单位**：规范正文写“毫秒”，但示例中出现 10 位秒级时间戳，设备侧需按位数判断（小于 1e12 视为秒），否则会出现 1970 年的时间点。

## 4.2  物模型服务的存储模型

物模型不直接塞进 ThingsBoard，而是由平台后端服务独立建模（PG 的 `plat_` schema），再同步为设备模板。建议的最小表结构如下（字段仅列关键项）。

**表 4-2  物模型服务存储模型**

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| plat_product | id, product_id, name, model, category_id, vendor, auth_type, protocol | 产品主数据；product_id 全局唯一 |
| plat_product_tsl | id, product_id, version, tsl_json, status, published_at | TSL 原文与版本；status 为 DRAFT/PUBLISHED/DEPRECATED |
| plat_tsl_property | product_id, tsl_version, key, name, data_type, mode, unit, min, max, step, mapping_json | 属性目录，供校验器与前端读取 |
| plat_tsl_event | product_id, tsl_version, event_id, name, event_type, params_json | 事件定义，供事件模板与保留键约定生成 |
| plat_tsl_action | product_id, tsl_version, action_id, name, input_json, output_json | 行为定义，供 RPC 模板生成 |
| plat_profile_binding | product_id, tsl_version, tb_profile_id, synced_at, sync_result | 产品与 ThingsBoard 模板的绑定关系，支持回滚 |

所有表以 (product_id, tsl_version) 为业务主键，保证同一产品的历史版本可追溯；设备侧上报的键值在接入时按“当前绑定版本”校验，避免灰度期间新旧定义混淆。

## 4.3  TSL 到设备模板的生成规则

生成器的输入是已发布的 TSL，输出是一组 ThingsBoard 工件（Device Profile、属性目录、影子与配置默认值、事件模板、RPC 模板）。规则如下表。

**表 4-3  TSL 到 ThingsBoard 工件的生成规则**

| TSL 元素 | 生成/映射规则 | ThingsBoard 工件 |
| --- | --- | --- |
| 产品信息 | 模板名=产品中文名+型号；描述写入 ProductId/CategoryId/版本 | Device Profile |
| 属性 mode=r | 键名保持原样；类型按附录 A 转换；单位/范围入元数据 | 遥测键（Telemetry） |
| 属性 mode=rw | 生成 `set` RPC 模板；start 值写 `shadow_desired` 共享属性作为期望值 | 遥测 + RPC + 1 个共享属性 |
| 枚举 mapping | 遥测仍存数值；mapping 作为元数据供前端翻译，不改变传输 | 属性目录 |
| 结构体 struct | 以 JSON 值上报；建议键名扁平化为 `struct.field` 便于聚合 | 遥测（JSON 值） |
| 事件 info | 保留 event_id、event_type、event_ts 与参数键 | 仅遥测，平台落事件表 |
| 事件 alert/fault | 同上，另在平台约定级别 MAJOR/CRITICAL | 仅遥测，级别由平台映射 |
| 行为 action | 方法名=actionId；params 作为请求体；response 作为返回体 | RPC 模板 |
| required=true | 生成接入校验规则：缺失则报文标记为不合规 | 校验器规则 |

生成器是幂等的：同一 TSL 版本重复执行只做差异更新；模板中由平台托管的字段（名称、描述、事件约定、RPC 模板）不允许人工修改，其余字段（界面图标、队列）可保留人工配置。生成模板时由平台后端服务以目标**厂商租户**的服务账号调用 ThingsBoard API，模板落在该租户内，厂商之间互不可见。工具实现见附录 D 的 `tsl2tb.py`。若希望先把样例跑通、暂不建物模型服务，按 4.6 的最小实现路径操作即可。

## 4.4  校验、发布与版本管理

**两级校验。** 结构层用 JSON Schema 校验必填字段、类型与枚举；业务层校验标识符唯一性、取值范围合理性、单位与数据类型匹配、功能点总数不超过规范的 100 项限制。校验不通过不允许发布。

**发布流程。** TSL 状态机为 草稿（DRAFT）→ 已发布（PUBLISHED）→ 已废弃（DEPRECATED）。发布动作触发模板同步与缓存刷新；废弃版本仍保留历史数据可读，但新设备不得绑定。

**兼容性规则。** 新增属性、放宽取值范围属于兼容变更，可在原版本上小版本递增；删除属性、修改数据类型、收窄范围属于破坏性变更，必须升级产品版本（新 ProductID）并制定迁移方案。由于 ThingsBoard 的设备模板没有“版本”概念，平台以 `profile_binding` 记录绑定关系，必要时采用“新建模板 + 批量迁移设备”的方式实现灰度。

## 4.6  以 9HYN9PJNOY 为例：哪些直接用、哪些只需少量开发

结论先说：这套物模型在社区版上**不需要先建库、建服务**。Device Profile 只定义传输方式与队列；遥测键是 schema-less 的，任何键都会被接收，33 个属性不需要任何 DDL。真正需要持久化的是 TSL 的定义信息（中文名、单位、范围、必填），而社区版模板没有自定义字段，最省事的办法是把 TSL 原文存成**产品资产的一个属性**。校验用一条规则链完成，事件随遥测上报、由平台落事件表。

**表 4-5  9HYN9PJNOY 的每个 TSL 元素落在哪、要不要写代码**

| TSL 元素 | ThingsBoard 原生承载 | 开发量 |
| --- | --- | --- |
| `profile.ProductId` / `CategoryId` / `version` | 设备模板描述 + 产品资产属性 `product_id`、`category_id`、`tsl_version` | 0，界面或 REST 配置 |
| `properties[].id`（33 个） | 遥测键，键名原样保留（如 `accX`、`rssi`） | 0，无需声明 |
| `properties[].name` / `desc` / `unit` / `min` / `max` / `step` / `required` | 整份 TSL 存产品资产属性 `tsl_json`；平台侧按需读取 | 0，一次写入 |
| `mode=r`（本样例全部） | 仅遥测，设备上报即入库 | 0 |
| `mode=rw` | 遥测上报 + `set` RPC 下发；`start` 写 `shadow_desired` 作期望值 | 少量，开通脚本 10 行 |
| `events[].type=info` | 遥测保留键，规则链过滤后只做展示 | 0 |
| `events[].type=alert/fault` | 遥测保留键 `event_type`，平台按 MAJOR/CRITICAL 落事件表 | 0，无需节点 |
| `actions[].id` | RPC 方法名=`actionId`，参数与返回值按 TSL | 0，设备侧实现 |
| `required=true` 与类型/范围校验 | 规则链脚本节点比对设备属性 `tsl_schema`（压缩 schema） | 少量，约 60 行 JS |
| 物模型浏览/编辑 | 原生“实体详情 → 属性”直接看 JSON；要好界面再做 Widget | 0，界面增强属后续 |

据此分三档落地，本项目建议从 L1 起步：

- **L0 纯原生**：模板、设备、凭证、遥测、原生仪表板。能采数、能看图，但报文没人校验，错键、错类型会静默入库。
- **L1 少量开发（推荐）**：在 L0 之上加一条规则链做 TSL 校验与事件识别，再加一个开通脚本处理 `rw` 默认值。总代码量约 60 行，全部是配置与脚本，不改内核。
- **L2 服务化**：把 4.2 的物模型表建到平台后端服务里，管版本、发布流、灰度与差异同步。等产品数超过十几个、或需要严格审计时再上。

**落地步骤（4 个动作、6 个 REST 调用）。** 下述接口均以厂商租户管理员身份调用，`tb_import_9HYN9PJNOY.json` 已把请求体按顺序列好。

**表 4-6  最小实现的步骤与接口**

| 步骤 | 动作 | 接口 |
| --- | --- | --- |
| 1 | 创建产品模板，描述里带 ProductId/CategoryId/版本 | `POST /api/deviceProfile` |
| 2 | 创建产品资产，把 `tsl_json` 等属性写进去 | `POST /api/asset`，再 `POST /api/plugins/telemetry/ASSET/{id}/attributes/SERVER_SCOPE` |
| 3 | 按 DeviceName 批量建设备，取回 Access Token | `POST /api/device`，`GET /api/device/{id}/credentials` |
| 4 | 给设备写 `tsl_version` 属性，便于校验时判断用哪版定义 | `POST /api/plugins/telemetry/DEVICE/{id}/attributes/SERVER_SCOPE` |

设备侧随后用 Token 连 1883/8883，向 `v1/devices/me/telemetry` 发一条最简报文即可验证：

*图 4-2  验证用最简遥测报文*

```
{ "accX": 0.12, "gyroX": -3.5, "rssi": -62, "bssid": "aa:bb:cc:dd:ee:ff", "temp": 41.2 }
```

**校验规则链（L1 的核心，约 60 行）。** 规则链里拿不到数据库，所以先由开通脚本把校验所需字段压缩成 `tsl_schema`，写进设备的 server 属性。节点顺序：消息类型过滤（只处理 `POST_TELEMETRY_REQUEST`）→ 取属性（server scope 取 `tsl_schema`、`tsl_version`，节点注入 `metadata.ss_*`）→ 脚本校验 → 分流（合法继续入库/外发，非法不落遥测）。压缩 schema 的结构、下发方式与完整规则见 4.7.4。

*图 4-3  TSL 校验脚本节点*

```
// 规则链脚本节点：按压缩 schema 校验键名、类型与范围
// 前置：originator attributes 取 server 属性 tsl_schema（metadata.ss_tsl_schema）
var out = { msg: msg, metadata: metadata, msgType: msgType };
var raw = metadata.ss_tsl_schema;
if (!raw) { metadata.tsl_invalid = ''; return out; }          // 未下发：放行，便于灰度

var schema;
try { schema = (typeof raw === 'string') ? JSON.parse(raw) : raw; }
catch (e) { metadata.tsl_invalid = '_schema:parse'; return out; }
var keys = schema.keys || schema, strict = schema.strictUnknown === true, bad = [];

Object.keys(msg).forEach(function (k) {
  var v = msg[k], d = keys[k];
  if (!d) { if (strict) { bad.push(k + ':unknown'); } return; }
  var t = d.t, ok;
  if (t === 'int' || t === 'timestamp' || t === 'enum') { ok = (typeof v === 'number' && v % 1 === 0); }
  else if (t === 'float') { ok = (typeof v === 'number'); }
  else if (t === 'bool') { ok = (typeof v === 'boolean' || v === 0 || v === 1); }
  else if (t === 'string') { ok = (typeof v === 'string'); }
  else { ok = true; }
  if (!ok) { bad.push(k + ':' + t); return; }
  if (typeof v === 'number') {
    if (typeof d.min === 'number' && v < d.min) { bad.push(k + ':min'); }
    if (typeof d.max === 'number' && v > d.max) { bad.push(k + ':max'); }
  }
});
Object.keys(keys).forEach(function (k) {
  var d = keys[k];
  if (d && d.req === true && !(k in msg)) { bad.push(k + ':missing'); }
});
metadata.tsl_invalid = bad.join(',');
return out;
```

后续节点读 `metadata.tsl_invalid`：为空走 `save timeseries`；非空则不进入遥测分支，改为写 `tsl_invalid_keys` 属性（或发 Kafka 的 `iot.telemetry.rejected`），供接入看板统计。这样既不丢数据，也不让脏数据污染时序库。

**表 4-7  最小实现的工作量估算**

| 事项 | 做法 | 人天 |
| --- | --- | --- |
| 模板、产品资产、设备与凭证 | `tsl2tb.py` 生成的 6 步 REST 清单 | 0.5 |
| TSL 校验规则链 | 5 个内置节点 + 约 60 行 JS | 2 |
| 事件识别（alert/fault） | 保留键约定 + 平台映射级别，无需告警节点 | 0.5 |
| `rw` 的 `set` RPC 与期望值初始化 | 10 行开通脚本 | 0.5 |
| 仪表板（最新值、曲线、异常计数） | 原生组件 | 0.5 |
| 合计 | — | 约 4.5 |

**不建议的三种做法。** 一是给每个属性建表或建 33 个资产，纯属把 schema-less 的存储又做成关系模型；二是 fork 内核去改主题或认证，升级会一直被卡住；三是把整份 TSL 塞进模板 `description`，那里只适合放摘要（ProductId、版本、属性个数），正文应放属性。

这条路径不依赖新后端：TSL 元数据先放产品资产属性，能快速验证“产品—设备—遥测”链路。平台后端服务（第 7 章）上线后，元数据迁到 `plat_tsl_*`，产品资产可只留作演示数据。

产物：`tb_artifacts_9HYN9PJNOY.json` 含模板、33 条属性目录、影子与配置默认值与导入清单；`tb_import_9HYN9PJNOY.json` 是可直接执行的 6 步 REST 清单；转换器 `work/tsl2tb.py` 支持 `--devices` 指定样例设备数量，对任意符合规范的 TSL 通用。

## 4.7  标准物模型的完整实现：定义时校验、发布时同步、运行时拦截

“标准物模型”不是一份 JSON 文件，而是四个动作都能闭环：**定义时有校验、发布时有同步、运行时有拦截、对外有目录**。4.6 是过渡做法（产品资产存 TSL），本节是目标形态，落在 platform-service 的 `tsl` 模块里。

### 4.7.1  定义时校验

结构层用 JSON Schema 保证字段、类型、枚举合法；业务层用规则引擎保证标识符、范围、枚举映射、结构体与功能点数量合法。两层都不通过就不允许保存或发布。

**表 4-8  校验规则与处置**

| 层 | 规则 | 错误码 | 处置 |
| --- | --- | --- | --- |
| 结构 | 必填字段、枚举取值、字符串长度、数组上限 | `*_MISSING`、`TYPE_INVALID`、`STRING_LENGTH` | 阻断保存 |
| 结构 | 标识符格式（英文/下划线开头，≤50，仅英文数字下划线） | `ID_INVALID` | 阻断保存 |
| 结构 | 属性 / 事件 / 行为 / 参数标识符唯一 | `ID_DUP`、`EVENT_ID_DUP`、`ACTION_ID_DUP`、`PARAM_DUP` | 阻断保存 |
| 业务 | 数值范围自洽（min≤max、start 在范围内、step≥0、int 不越 32 位） | `RANGE_REVERSED`、`START_OUT_OF_RANGE`、`STEP_INVALID`、`INT_RANGE` | 阻断发布 |
| 业务 | 枚举必须有 ≥2 项 mapping，枚举型键值为数字 | `ENUM_MAPPING`、`ENUM_KEY` | 阻断发布 |
| 业务 | 结构体字段非空、不嵌套结构体 | `STRUCT_EMPTY`、`STRUCT_NESTED` | 阻断发布 |
| 业务 | 事件/行为参数与结构体字段不允许结构体 | `STRUCT_NOT_ALLOWED` | 阻断发布 |
| 业务 | 功能点总数（属性+事件+行为）≤100 | `FUNCTION_POINTS` | 阻断发布 |
| 业务 | 与平台约定键同名（`ts`、`event_id`、`event_type`、`event_ts`） | `ID_RESERVED` | warning，接入文档说明 |
| 运行 | 未定义键、类型不符、超出 min/max | 规则链 `metadata.tsl_invalid` | 不落遥测，写异常属性或转 Kafka |
| 同步 | 模板生成/调用 TB 失败 | `SYNC_FAILED` | 保持 DRAFT，写同步日志，可重试 |

### 4.7.2  发布与同步

六步固定流程，任何一步失败都不改变线上生效版本。

**表 4-9  发布与同步流程**

| 步骤 | 动作 | 落库/副作用 |
| --- | --- | --- |
| 1 | 保存草稿：按 `(product_id, version, checksum)` 幂等写入 | `plat_product_tsl` 状态 DRAFT |
| 2 | 结构校验 + 业务校验 | 失败返回逐条错误，不落库 |
| 3 | 生成工件：Profile 骨架、属性目录、影子与配置默认值、事件模板、RPC 模板 | 内存/临时结果 |
| 4 | 发布：状态置 PUBLISHED，属性/事件/行为目录落表 | `plat_tsl_*` + `published_at` |
| 5 | 同步模板：调用 TB `deviceProfile` API，幂等比对名称与描述 | `plat_profile_binding` 记录 `tb_profile_id` 与 `sync_result` |
| 6 | 灰度与回滚：新版本先绑定少量设备（设备属性 `tsl_version`），确认后全量；回滚只改绑定 | 绑定变更留审计，历史版本不删 |

### 4.7.4  运行时校验（规则链）

**为什么要在设备上贴 schema。** ThingsBoard 的规则链拿不到你的数据库，脚本里无法查 `plat_tsl_property`；如果每条消息都回调后端换 schema，等于把规则链变成了 HTTP 客户端。折中做法是：定义时把校验所需字段压缩成一份 `tsl_schema`，随设备开通写入其 **server 属性**，规则链用 `originator attributes` 节点取出、脚本比对。设备看不到该属性，也不需要推送，不会增加下行流量。

**压缩 schema 的结构。** 只保留类型、范围、枚举、必填，去掉名称、描述、中文名等展示信息。9HYN9PJNOY 压缩后为 **33 个键、3 311 字节**，约为原 TSL 的 38%。

```
{
  "schemaVersion": "1.0",
  "productId": "9HYN9PJNOY",
  "strictUnknown": false,
  "keys": {
    "accX": { "t": "float", "mode": "r", "min": -4.0, "max": 4.0, "unit": "g" },
    "rssi": { "t": "int", "mode": "r", "min": -100.0, "max": 0.0 },
    "bssid": { "t": "string", "mode": "r" }
  }
}
```

生成用 `work/make_schema.py`（与后端 `CompactSchema.java` 同一规则），写入用 `work/push_tsl_schema.py`：

```
python work/make_schema.py 9HYN9PJNOY.json -o work/tsl_schema_9HYN9PJNOY.json
python work/push_tsl_schema.py --host http://thingsboard:8080 --token "$TOKEN" \
    --schema work/tsl_schema_9HYN9PJNOY.json --profile-id "$PROFILE_ID"
```

`tsl_schema` 存成字符串而不是 JSON 对象：规则链 metadata 是 `Map<String,String>`，字符串能保证 `JSON.parse` 一定可用；脚本同时兼容被解析成对象的情况。

**什么时候下发。** 设备开通时立即写；TSL 发布新版本时，新设备写新版，存量设备由异步任务分批刷新（每批 200 台、间隔 1 秒）；TSL 回滚则重新下发旧版 schema，规则链无需改动。2 万台全量刷新约 2 万次属性写，按 50 次/秒约 7 分钟。

**节点配置。** 在根链上插入三个节点，不动其他分支。

**表 4-11  校验节点配置**

| 节点 | 类型 | 关键配置 | 说明 |
| --- | --- | --- | --- |
| 消息类型 switch | message type switch | 已有节点 | `Post telemetry` 连到新节点 |
| 取属性 | originator attributes | server attributes：`tsl_schema`、`tsl_version` | 只勾 server scope，不勾 latest values |
| 校验脚本 | script | 见下方脚本 A | 输出 `metadata.tsl_invalid` |
| 条件判断 | js switch | 脚本 B | True=合法，False=非法 |
| 保存遥测 | save timeseries | 原节点 | 只接 True 分支 |
| 拒收 | script + save attributes / kafka | 脚本 C | 见拒收接法 |

节点连接：`switch(Post telemetry) → 取属性 → 校验脚本 → js switch`，`True → save timeseries`，`False → 拒收`。

**脚本 A：校验。** 注意规则链里的 `msg` 就是 values 层（Transport 已拆包），`ts` 在 `metadata.ts`，不要写 `msg.values`。

```
var out = { msg: msg, metadata: metadata, msgType: msgType };
var raw = metadata.ss_tsl_schema;
if (!raw) { metadata.tsl_invalid = ''; return out; }          // 未下发：放行，便于灰度

var schema;
try { schema = (typeof raw === 'string') ? JSON.parse(raw) : raw; }
catch (e) { metadata.tsl_invalid = '_schema:parse'; return out; }
var keys = schema.keys || schema, strict = schema.strictUnknown === true, bad = [];

Object.keys(msg).forEach(function (k) {
  var v = msg[k], d = keys[k];
  if (!d) { if (strict) { bad.push(k + ':unknown'); } return; }
  var t = d.t, ok;
  if (t === 'int' || t === 'timestamp' || t === 'enum') { ok = (typeof v === 'number' && v % 1 === 0); }
  else if (t === 'float') { ok = (typeof v === 'number'); }
  else if (t === 'bool') { ok = (typeof v === 'boolean' || v === 0 || v === 1); }
  else if (t === 'string') { ok = (typeof v === 'string'); }
  else { ok = true; }
  if (!ok) { bad.push(k + ':' + t); return; }
  if (typeof v === 'number') {
    if (typeof d.min === 'number' && v < d.min) { bad.push(k + ':min'); }
    if (typeof d.max === 'number' && v > d.max) { bad.push(k + ':max'); }
  }
});
Object.keys(keys).forEach(function (k) {
  var d = keys[k];
  if (d && d.req === true && !(k in msg)) { bad.push(k + ':missing'); }
});
metadata.tsl_invalid = bad.join(',');
return out;
```

**脚本 B：条件判断。**

```
return (metadata.tsl_invalid || '') === '';
```

**脚本 C：拒收（转属性）。**

```
return { msg: { tsl_invalid_keys: metadata.tsl_invalid, tsl_invalid_at: Date.now() },
         metadata: metadata, msgType: 'POST_ATTRIBUTES_REQUEST' };
```

**拒收接法。** 三种选一种，不建议对单条坏报文发通知——一台设备配置错就能在几分钟内产生上万条事件，把通知通道打爆。

**表 4-12  拒收分支的三种接法**

| 接法 | 实现 | 适用 |
| --- | --- | --- |
| 落属性 | 脚本 C + save attributes（SERVER_SCOPE） | 无 Kafka，调试与小规模 |
| 发 Kafka | Kafka 节点发 `iot.telemetry.rejected`，key 用 deviceId | 已接 Kafka，后端统计与回查 |
| 仅记日志 | log 节点打 WARN | 灰度期观察，不长期用 |

**性能与限制。** 每条遥测都会触发一次属性查询；脚本本身是毫秒级，瓶颈在属性读取。

**表 4-13  运行时校验的边界**

| 限制 | 说明 | 规避 |
| --- | --- | --- |
| 属性查询开销 | 每消息一次，建议 <200 条/秒 | 高速率改 Kafka + ingest 校验 |
| 网关子设备 | `v1/gateway/telemetry` 的 originator 是网关，取到网关 schema | 网关场景走 ingest，或给网关合并 schema |
| 属性类消息 | `Post attributes` 分支未校验 | 需要时复制同一套节点改接 |
| 结构体 | 只校验 `t=json`，不做深层 | 先扁平化再接入 |
| 跨字段规则 | 如“A 与 B 不能同时为 0” | 规则链可写但难维护，放 ingest |
| 版本差异 | 各版本节点类名与配置键略有差异 | 以界面保存后的导出为准 |

### 4.7.5  验收用例

**表 4-14  校验验收用例**

| 输入 | 期望错误码 |
| --- | --- |
| 属性 id 以数字开头，如 `1speed` | `ID_INVALID` |
| 两个属性同名，如两个 `speed` | `ID_DUP` |

| 属性 + 事件 + 行为总数 101 | `FUNCTION_POINTS` |

### 4.7.6  产物与使用

- `schemas/tsl-v1.5.schema.json`：结构层 Schema，可直接接入表单校验或 CI。
- `work/validate_tsl.py`：业务层校验器，无第三方依赖；样例 9HYN9PJNOY 通过（0 error、1 warning），反例夹具 `work/fixtures/invalid_tsl.json` 报出 14 条错误、3 条警告。
- `sql/plat_tsl.sql`：`plat_*` 表结构，含状态机与目录索引。
- `work/make_schema.py` 与 `work/push_tsl_schema.py`：压缩 schema 的生成与批量下发。
- `rules/tsl_validate.js`：早期脚本版本，语义与 4.7.4 一致，以本节为准。

建议把 `validate_tsl.py --json` 挂到 CI：TSL 提交、模板生成、发布三个环节各跑一次，同一份规则只有一处实现，避免“库里能存、线上报错”。
