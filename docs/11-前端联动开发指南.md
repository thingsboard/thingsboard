# 前端加页面 + 产品/物模型联动开发指南

> *中铁信科物联网平台文档集 ｜ 实施指南* ｜ [总目录](../README.md) ｜ 前置 [04-物模型](04-物模型.md) ｜ 下一份 [12-遥测单通道设计](12-遥测单通道设计.md)

目标：在 ThingsBoard 现有前端（`ui-ngx`）里加一个“产品与物模型”页面，页面只调新开发的独立后端（platform-service）；后端在保存产品与物模型时，自动调用 ThingsBoard 的 REST 接口创建设备模板（Device Profile）、产品资产（Asset）与 TSL 属性。

## 1  交付清单

| 位置 | 文件 | 作用 |

| `ui-ngx/src/app/modules/crec-iot/` | `crec-iot.module.ts` | 模块与子路由 |
| 同上 | `crec-iot.service.ts` | 调后端；用 `HttpBackend` 绕过 TB 拦截器 |

| 同上 | `product-edit.component.ts` | 新建对话框：产品信息 + TSL + 结果/错误展示 |

| 同上 | `TbRestClient.java` | TB REST 客户端（登录缓存、401 重试、按名幂等） |

## 2  前端接入五步

### 2.1 挂路由

`ui-ngx/src/app/app-routing.module.ts` 的 `routes` 里加一条懒加载路由（放在 `ROUTES` 常量或 `children` 中，与 TB 其他页面同级）：

```ts
{
  path: 'crec-iot',
  loadChildren: () => import('./modules/crec-iot/crec-iot.module').then(m => m.CrecIotModule)
}
```

如果 TB 的 `app-routing.module.ts` 用 `...routes` 常量拼装，按同样风格追加即可；注意不要放进 `noAuth` 路由表，本页面要求登录。

### 2.2 注册菜单

菜单在 `ui-ngx/src/app/core/services/menu.service.ts` 的 `getMainMenuItems()` 里生成。找到返回 `menuItems` 的数组，追加一项：

```ts
import { MenuSection } from '@core/services/menu.models';   // 版本不同路径可能为 shared/models/menu.models

// 在 menuItems 数组里追加
{
  id: 'crec_iot',
  name: '物联网平台',
  type: 'link',
  path: '/crec-iot',
  icon: 'devices_other',
  opened: false
}
```

菜单结构版本间略有差异（有的版本要求 `MenuSection` 包一层 `pages` 数组、有的直接是 `MenuItem`）。以同文件里相邻菜单项为准照抄结构，只改 `id`/`name`/`path`/`icon`，最稳妥。

### 2.3 模块与路由

`crec-iot.module.ts` 已给出：`RouterModule.forChild([{ path: '', component: ProductListComponent }])`，因此 `/crec-iot` 直接落到列表页。

### 2.4 服务：必须绕开 TB 的拦截器

这是最容易踩的坑。TB 的 `defaultHttpInterceptor`（`src/app/core/interceptors/default-http.interceptor.ts`）会：

- 给请求统一加 `X-Authorization: Bearer <TB JWT>`；
- 收到 401 时触发 TB 自身的刷新/登出逻辑。

我们的后端不是 TB，401 语义不同，被 TB 拦一次会把用户踢出登录页。所以 `crec-iot.service.ts` 里用 `HttpBackend` 直接构造一个干净的 `HttpClient`：

```ts
constructor(backend: HttpBackend, private auth: AuthService) {
  this.http = new HttpClient(backend);       // 不经过任何 interceptor
}
```

### 2.5 文案（可选）

若要中英文都正常，在 `ui-ngx/src/assets/locale/locale.constant-zh_CN.json` 与 `en_US` 里补 `menu.crec-iot` 等键；菜单项也可直接用中文字符串，先跑通再补 i18n。

## 3  鉴权：用 TB 的 JWT 换后端会话

页面运行在 TB 里，浏览器本来就有 TB 的 JWT。这里把它当作**身份断言**：前端把 JWT 放 `X-Authorization` 传给 platform-service，后端调 TB `/api/auth/user` 校验（缓存 60 秒），再**用服务账号**去写 TB。

这样做的取舍：

| 做法 | 优点 | 代价 |
| --- | --- | --- |
| 复用 TB JWT 做身份断言（本文） | 不用二次登录，体验一致 | 后端必须校验，且要防越权 |
| 页面内再做一次平台登录 | 与 TB 会话完全解耦 | 双登录，用户体验差 |
| 前端直连 TB API | 省后端 | 违反“浏览器不直连 TB”原则，凭证散落 |

主文档里“浏览器不持有 TB JWT”约束的是**业务系统**；TB 自身 UI 必然持有，因此这里的边界是：**JWT 只用于身份校验，写 TB 一律在后端用服务账号完成**。

**必须补的越权过滤**（骨架里留了 TODO）：`verifyUser` 返回的用户带 `tenantId`，把它与 `plat_product.vendor_tenant_id` 比对，厂商只能看/改自己的产品；sysadmin 可看全部。示例如下：

```java
JsonNode user = tb.verifyUser(jwt);
String tenantId = user.path("tenantId").path("id").asText();
String authority = user.path("authority").asText();
// authority=tenant_admin 时，list/create 都带上 tenantId 过滤
```

## 4  后端接口契约

| 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| GET | `/api/crec/products` | — | `ProductItem[]` |
| POST | `/api/crec/products` | `CreateReq`（含 TSL） | `CreateResp` |
| PUT | `/api/crec/products/{pid}/tsl` | `TslUpdateReq` | `CreateResp` |
| POST | `/api/crec/products/{pid}/devices` | `{"names":[...],"labelPrefix":""}` | `DeviceResp[]`（含一次性 Access Token） |
| POST | `/api/crec/products/{pid}/sync` | — | `SyncResp`（重新对齐 TB） |

错误约定：

| 状态码 | 场景 | 响应体 |
| --- | --- | --- |
| 400 | TSL 校验失败 | `{"message":"参数校验失败","issues":[{code,path,message}]}` |
| 401 | JWT 无效 | `{"message":"登录状态无效或已过期"}` |
| 502 | TB 调用失败 | `{"message":"同步 ThingsBoard 失败：…","retry":"/api/crec/products/{pid}/sync"}` |

前端把 `issues` 直接渲染成错误清单，用户改完 TSL 再提交，不用猜。

## 5  保存一次的完整时序

```
前端 POST /api/crec/products {productId,name,model,categoryId,tslVersion,tsl}
 └─ 1 校验 JWT（TB /api/auth/user，缓存 60s）
 └─ 2 定义时校验（TslValidator：id/类型/范围/枚举/功能点）
 └─ 3 生成压缩 schema（CompactSchema，33 键约 3.3KB）
 └─ 4 本地落 DRAFT（plat_product + plat_product_tsl）
 └─ 5 TB：按 name 查设备模板 → 有则更新、无则创建 → profileId
 └─ 6 TB：按 name 查产品资产 → 建/更新 → assetId
 └─ 7 TB：写资产 SERVER_SCOPE 属性（tsl_json、tsl_schema、计数、版本）
 └─ 8 本地：写 plat_profile_binding、状态置 PUBLISHED
 └─ 9 返回 {tbProfileId, tbAssetId, 属性/事件/行为数, schemaBytes}
```

任何一步失败：第 4 步之后的 DRAFT 保留，返回 502，用户可点“重新同步”（`/sync` 幂等重跑第 5~8 步）。

## 6  自动调 TB 的实现要点

**幂等。** TB 的 `name` 在租户内唯一，直接建会报错。`TbRestClient` 统一“先按 name 查、存在则带 `id` 更新”：

```java
JsonNode existing = findProfileByName(token, name);
if (existing != null) { body.put("id", existing.path("id")); }
```

**模板内容。** 只写 TB 支持的字段，多写会被忽略或报错：

```json
{
  "name": "WiFi诊断终端 9HYN9PJNOY",
  "description": "ProductId=9HYN9PJNOY; CategoryId=1; TSL v1.0; 属性 33 个",
  "type": "DEVICE",
  "transportType": "DEFAULT",
  "profileData": {
    "configuration": { "type": "DEFAULT" },
    "transportConfiguration": { "type": "DEFAULT" },
    "provisionConfiguration": { "type": "DISABLED" },
    "alarms": []
  }
}
```

`description` 里的 ProductId 是 TB 侧唯一的“产品线索”，用于人工核对与对账；结构化查询仍走 `plat_product`。

**产品资产属性。** 一次写全，规则链与前端目录都依赖它：

| 属性 | 示例 | 用途 |
| --- | --- | --- |
| `product_id` | `9HYN9PJNOY` | 反查产品 |
| `category_id` | `1` | 分类 |
| `tsl_version` | `1.0` | 版本 |
| `property_count` / `event_count` / `action_count` | `33` / `0` / `0` | 列表展示 |
| `tsl_json` | 全文 | 追溯原文 |
| `tsl_schema` | 压缩 schema 字符串 | 规则链校验 |

**批量建设备。** 每个设备建完立即写 `tsl_version` 与 `tsl_schema`（规则链校验依赖它，见设计说明书 4.7.4），再取 Access Token。Token 只返回一次，前端必须提供下载；后端不要长期明文存。

**规则链自动下发。** 发布动作除了建设备模板，还要为该产品建一条“遥测入湖链”并绑定 `DeviceProfile.defaultRuleChainId`。实现是 `TbRuleChainProvisioner`：读九节点模板、替换 Kafka 地址与 topic、用稳定节点 id 幂等保存，最后改模板绑定。节点配置、端点与版本适配见《物模型遥测入湖链路设计》5.4。

**失败补偿。** 不做跨库事务：本地 DRAFT → 调 TB → 成功才置 PUBLISHED。定时对账任务比较 `plat_profile_binding` 与 TB 实体，修复“本地已发布、TB 无模板”的漂移；规则链 id 记在 `plat_profile_binding.sync_result`，对账时一并核对。

## 7  入口分流（Nginx）

```nginx
location /crec-api/ {
    proxy_pass http://platform-service:8080/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}
location /api/      { proxy_pass http://thingsboard:8080/api/; }
location /          { try_files $uri $uri/ /index.html; }
```

前端服务里 `BASE = '/crec-api'`，因此 `/crec-api/api/crec/products` → `platform-service:8080/api/crec/products`。这样与 TB 的 `/api` 完全隔离，前端不需要跨域配置。

## 8  本地联调

```bash
# 1) 建产品 + 物模型（TSL 用 9HYN9PJNOY.json 全文）
curl -s -X POST http://localhost:8080/api/crec/products \
  -H "X-Authorization: Bearer $TB_JWT" -H "Content-Type: application/json" \
  -d '{"productId":"9HYN9PJNOY","name":"WiFi诊断终端","model":"9HYN9PJNOY",
       "categoryId":"1","tslVersion":"1.0","tsl":{ … }}'

# 期望
# {"productId":"9HYN9PJNOY","tslVersion":"1.0","tbProfileId":"...","tbAssetId":"...",
#  "propertyCount":33,"eventCount":0,"actionCount":0,"schemaBytes":3311,"status":"PUBLISHED","warnings":[]}

# 2) 批量建 2 台设备
curl -s -X POST http://localhost:8080/api/crec/products/9HYN9PJNOY/devices \
  -H "X-Authorization: Bearer $TB_JWT" -H "Content-Type: application/json" \
  -d '{"names":["WIFI_DIAG_0001","WIFI_DIAG_0002"],"labelPrefix":"样机-"}'
```

验证点：
1. TB 设备模板列表出现 `WiFi诊断终端 9HYN9PJNOY`，描述含 ProductId。
2. TB 资产列表出现 `产品 9HYN9PJNOY`，属性里有 `tsl_json` 与 `tsl_schema`。
3. 两台设备各自带模板、凭证可用，`tsl_version=1.0`。
4. 用 Access Token 发一条遥测，规则链校验通过并入库。

## 10  版本与依赖注意

- **Angular 版本**跟 TB 版本走（3.6 用 Angular 15，3.7 用 15/16），`@angular/material` 版本要一致；`MatDialog`、`MatFormField` 等模块已在依赖里，无需新增包。
- **`assetProfileId`**：TB 3.5+ 资产必须归属资产模板。`upsertAsset` 现在用 `type: "product"`，若目标版本报 “Asset profile is required”，改为先查默认资产模板再带 `assetProfileId`。
- **构建**：`ui-ngx` 下用 TB 自带脚本（`yarn build:prod` 或 `pnpm build:prod`，按版本 README），产物替换 Nginx 的 `root` 目录；只在 `modules/crec-iot/` 与菜单、路由两个文件里留差异，升级好合并。
- **后端依赖**：`spring-boot-starter-web`、`spring-boot-starter-jdbc`、`jackson`；不需要引入 TB 的 jar，全部通过 HTTP 契约交互。
- **时区**：TB 与后端统一 UTC 存储，前端按浏览器时区展示。
