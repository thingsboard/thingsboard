# 5  设备接入设计（ThingsBoard 内置 MQTT）

> *中铁信科物联网平台文档集 ｜ 第 5 章* ｜ [总目录](../README.md) ｜ [设计说明书总览](02-总体设计.md) ｜ 上一章 [物模型](04-物模型.md) ｜ 下一章 [数字孪生与数据加工](06-数字孪生与数据加工.md)

平台使用 **ThingsBoard 社区版**，不部署 EMQX、Mosquitto 等外部 Broker。设备直连底座自带的 MQTT Transport（1883 / 8883），凭证由底座校验，主题必须使用 ThingsBoard 原生规范（`v1/devices/me/*` 与 `v1/gateway/*`），底座不接受自定义主题。

这意味着“在平台侧做协议转换”的路走不通：社区版没有 Broker 认证回调，自研 transport 服务又会被排除在官方升级路径之外。因此，**腾讯 IoT 的 `$thing` 语义在数据契约层保持不变（产品、设备、物模型、属性/事件/行为），报文层由设备侧 SDK 完成一次转换**，平台只承接 ThingsBoard 原生报文。

## 5.1  接入拓扑与三种设备形态

**表 5-1  三种设备接入形态**

| 形态 | 设备侧 | 平台侧 | 适用 |
| --- | --- | --- | --- |
| 直连 | 按 ThingsBoard 主题与凭证开发/改固件 | 仅配置 MQTT Transport 与设备凭证 | 新建项目、自研终端 |
| 存量改造 | 固件升级：改用 TB 凭证与主题，业务逻辑不动 | 无需额外组件 | 存量腾讯设备 |
| 设备 SDK | 集成平台 SDK（封装主题与凭证） | 同直连 | 厂商愿改固件但不想理解 TB 协议 |

三种形态最终在 ThingsBoard 中完全同构：同一套 Device Profile、同一套遥测键。差异只发生在“消息到平台之前”的这一跳。

传输侧建议在底座前放一对 HAProxy / Nginx stream 做统一入口：终结 TLS、限制单 IP 连接数、按设备维度限流。这不是 Broker，不参与协议解析，只解决社区版缺少的连接治理能力。

## 5.2  凭证与三元组映射

社区版支持三种设备凭证，直接使用即可，不需要自建认证服务。

**表 5-2  设备凭证与腾讯三元组的对应**

| 凭证方式 | 接入方式 | 与腾讯三元组的对应 | 说明 |
| --- | --- | --- | --- |
| Access Token | MQTT 用户名填 Token | ProductId + DeviceName → 设备；DeviceSecret → Token | 一机一密，最简单，建议默认 |
| X.509 证书 | mTLS 双向认证 | 设备证书 | 高安全场景，需管理证书生命周期 |
| MQTT Basic | clientId / username / password | DeviceName → clientId；密钥 → password | 适合一账号多设备的第三方系统 |

三元组的落点是：`ProductId` → Device Profile（产品模板），`DeviceName` → `device.name`，`DeviceSecret` → Access Token 或 MQTT Basic 的密码。密钥密文入库、接口返回掩码、支持重置与禁用。

关于腾讯的动态 HMAC 签名：`username = ProductId + DeviceName; sdkappid; connid; expire`、`password = base64(HMAC_SHA1(rawKey, username)) + ";hmacsha1"` 这类签名需要在连接时逐次计算，而社区版 Transport 只做静态凭证校验，**平台侧无法验证**。处理方式只有一个：**存量设备升级固件，改用 TB 凭证**（Access Token / X.509 / MQTT Basic）。平台不设网关做签名代理，rawKey 在设备侧废弃或仅留在厂商内部。

设备采用**预创建**方式：关闭自动注册，按产品批量导入设备与凭证，校验命名规则与唯一性后再启用。

## 5.3  主题与报文

平台只认 ThingsBoard 原生主题。设备与平台之间的键值约定如下表，其中“腾讯语义”一列说明数据含义如何对应，而不是要求设备按腾讯主题发送。

**表 5-3  ThingsBoard 主题与腾讯语义的对应**

| ThingsBoard 主题 | 方向 | 用途 | 腾讯语义对应 |
| --- | --- | --- | --- |
| `v1/devices/me/telemetry` | 上行 | 属性上报、事件上报 | `$thing/up/property` 的 `report`、`$thing/up/event` |
| `v1/devices/me/attributes` | 上行 | 客户端属性（影子状态） | 设备侧影子 `reported` |
| `v1/devices/me/attributes` | 下行 | 共享属性（配置、期望值） | `$config/operation`、影子 `desired` |
| `v1/devices/me/attributes/request/{id}` | 上行 | 请求服务端属性 | 影子读 |
| `v1/devices/me/attributes/response/{id}` | 下行 | 服务端属性应答 | 影子读回执 |
| `v1/devices/me/rpc/request/{id}` | 下行 | 属性设置、行为调用 | `$thing/down/property` 的 `control`、`$thing/down/action` |
| `v1/devices/me/rpc/response/{id}` | 上行 | 控制/行为回执 | `$thing/up/property` 的 `control_reply`、`$thing/up/action` |
| `v1/gateway/connect` / `disconnect` | 上行 | 网关子设备上线/下线 | 网关型设备（可选） |
| `v1/gateway/telemetry` / `attributes` / `rpc` | 双向 | 网关代子设备收发 | 网关型设备（可选） |

报文约定：遥测支持两种载荷——扁平键值 `{"key": value}` 与带时间戳的 `{"ts": 1628646783000, "values": {...}}`。时间戳统一用毫秒，设备上报的秒级时间戳需在设备侧或网关侧乘 1000，否则会出现 1970 年的时间点。事件没有独立通道，用保留键表达：`event_id`、`event_type`、`event_ts`，其余参数作为普通遥测键一并上报，由平台事件中心识别并落事件表。

## 5.4  属性上报与远程控制

属性上报走遥测，不建属性实体：设备向 `v1/devices/me/telemetry` 发布，键名就是 TSL 的 `id`。完整的承载口径与 Attributes 白名单见《遥测单通道设计说明》第 3、5 节。

```
// 设备 → 平台
{ "ts": 1628646783000,
  "values": { "power_switch": 1, "brightness": 32, "rssi": -62 } }
```

*图 5-1  属性上报报文*

**上行一律遥测。** 无论 `mode` 是 `r` 还是 `rw`，设备上报的当前值都进遥测：只有一条链路、一套时间序列，聚合与查询不必区分“属性还是遥测”。

**下行用 RPC，不逐键下发属性。** `rw` 属性的写操作按 RPC 下发：应用调开放 API → 平台向 `v1/devices/me/rpc/request/{id}` 发 `{"method":"set","params":{"brightness":60}}` → 设备执行后回 `rpc/response/{id}`。TSL 里声明了 `actions` 的产品，行为调用走同一通道，`method` 即 `actionId`。

**只在这些数据上用 Attributes。** 属性适合“低频、可覆盖、非时序”的状态，因此只保留下表这些键，其余一律遥测。

**表 5-4  仅这些数据使用 Attributes**

| 键 | Scope | 内容 | 为什么用属性 |
| --- | --- | --- | --- |
| `tsl_version` / `tsl_schema` | server | 物模型版本与压缩 schema | 规则链校验只读，变化时整体替换 |
| `device_model` / `site_code` | server | 型号、绑定工点 | 静态元数据，不参与时序分析 |
| `device_uuid` / `tenant_id` | server | 设备 UUID 与租户 ID | 规则链外发信封要用，避免回查 |
| `cfg_json` | shared | 远程配置（采样周期、阈值） | 下发即覆盖，没有历史意义 |
| `shadow_desired` / `shadow_reported` | shared / client | 影子期望与上报 | 只需要当前值 |
| `fw_title` / `fw_version` / `fw_checksum` / `fw_size` | shared | OTA 目标固件 | ThingsBoard OTA 机制的约定 |

**不用的东西。** 不用 Alarm 实体承载异常（见 5.5 与 6.3）；不为每个 `rw` 属性建共享属性——属性会随 TSL 膨胀，且与遥测值双写容易出现不一致。

QoS 建议 1（至少一次），重复报文由设备侧用递增 `msgId` 或在平台侧按 `ts` 去重；社区版不缓存离线消息，断网期间的数据需在设备本地缓存，恢复后补传。

## 5.5  事件上报与事件识别

事件与属性走同一条通道：遥测。设备在 `v1/devices/me/telemetry` 里带三个保留键上报，参数作为普通遥测键一起发送：

```
{ "ts": 1628646783000,
  "values": { "event_id": "over_speed", "event_type": "alert",
              "event_ts": 1628646782000, "speed": 92.5, "limit": 80 } }
```

*图 5-2  事件上报报文*

规则链只做两件事：补 metadata（productId、deviceName、tslVersion）并把消息外发 Kafka；**不建告警实体**。

**平台如何识别。** ingest 消费后按 `event_type` 分流：`info` 落事件表（kind=info）；`alert` / `fault` 落事件表并标记级别（MAJOR / CRITICAL）。同一 `(device, event_id, event_ts)` 幂等，重复上报只留一条。

**表 5-5  事件类型与平台处理**

| 事件类型 | 腾讯示例 | 平台处理 | 级别 |
| --- | --- | --- | --- |
| info | 进出围栏、开关机 | 写事件表，时间线展示 | 不通知 |
| alert | 超速、低电量 | 写事件表，进入事件中心 | MAJOR |
| fault | 故障类型、严重等级 | 写事件表，进入事件中心，可附故障码 | CRITICAL |

**没有“活动/清除”状态。** 事件是“发生过的事实”，天然带时间戳；需要持续语义的（离线、指标越限）由事件中心生成带 `start_ts`/`end_ts` 的区间事件，恢复时补 `end_ts`，而不是维护一条长期挂着不动的告警。

**为什么不用 Alarm。** 一是 TSL 的 info/alert/fault 与 ThingsBoard 告警的“活动/确认/清除”生命周期不是一回事；二是告警页是运维视角，业务要的是事件时间线；三是告警在租户内产生，跨厂商汇总还要再造一套。统一用遥测 + 事件表，一套存储、一套查询、一套通知。

腾讯定义的 400/403/405/406 错误码属于其应用层语义，ThingsBoard 的 MQTT Transport 不返回这些码，而是直接断开非法连接或丢弃非法主题。若厂商确实需要按腾讯错误码排查，错误映射由设备侧 SDK 完成（校验失败时由 SDK 记录并按厂商约定上报），平台侧只记录接入日志。

## 5.6  行为调用与 RPC

行为对应双向 RPC：方法名为 `actionId`，`params` 为调用参数，设备返回的 `response` 作为 RPC 返回值。完整时序为：应用 → 开放 API → 平台 RPC（超时 10 秒）→ 设备 → RPC 响应 → 应用。

- **幂等**：平台侧以 RPC 请求 ID 为幂等键，重复调用返回缓存结果，不重复下发。
- **超时与降级**：10 秒未收到回执返回超时错误；对开锁、升降等关键动作，业务侧需补充“执行结果确认”（设备上报状态遥测），而不是仅依赖回执。
- **错误码对齐**：设备返回 `code≠0` 时，开放 API 统一转换为业务错误码，避免把平台异常暴露给调用方。

## 5.7  系统能力：OTA、配置与影子

社区版没有独立的 OTA 服务与影子服务，但用共享属性 + 遥测可以实现同等语义。

**表 5-6  系统能力与实现方式**

| 能力 | 平台实现 | 设备侧处理 |
| --- | --- | --- |
| 固件升级 | 固件作为资源上传；`fw_title`、`fw_version`、`fw_checksum`、`fw_size` 写入共享属性；升级状态用 `fw_state`、`fw_error` 遥测回传 | 订阅共享属性变更，下载并校验后上报进度 |
| 远程配置 | 共享属性 `cfg_json`（JSON 字符串）下发 | 订阅 `v1/devices/me/attributes`，应用配置并回写生效状态 |
| 设备影子 | 客户端属性（`shadow_reported`）+ 共享属性（`shadow_desired`）+ 最新遥测 | 上线后主动拉取 `attributes/request`，上报当前状态 |
| NTP | 平台不下发 NTP（社区版无此服务）；可由共享属性 `server_time` 提供参考时间 | 设备自建 NTP 或使用平台时间校准 |
| 广播 | 规则链按产品/租户批量下发 RPC | 逐台接收执行，网关型设备可批量代发 |

OTA 的约束：升级包大小与批量台数由部署环境决定，建议单包不超过 500MB、单批不超过 2000 台，升级失败自动回滚到上一版本，并在仪表板上跟踪升级率。

## 5.8  存量设备改造与接入治理

**统一走直连。** 存量腾讯设备不经过任何网关或代理：把固件升级到使用 ThingsBoard 凭证与主题的版本，直接连平台的 MQTT Transport。这样设备链路只有一跳，问题定位简单，也不需要在现场额外部署与运维一台网关。

**固件改造三件事。** 一是凭证：把 `ProductId`/`DeviceName`/`rawKey` 换成设备的 Access Token（或 X.509 / MQTT Basic），HMAC 签名逻辑删除；二是主题：`$thing/up|down/*` 改为 `v1/devices/me/telemetry|attributes|rpc/*`；三是报文键：属性键保持 TSL 的 `id` 不变，事件改用 `event_id`/`event_type`/`event_ts` 三个保留键。业务逻辑、采样频率、上报周期都不变，改造量集中在通信层。

**分批推进。** 按产品、按项目分批升级，升级前平台侧先建好模板与设备凭证，升级后用同一批设备做 A/B 验证（旧版本仍在腾讯云、新版本进平台）；验证通过再停旧通道。批量升级期间用遥测 `fw_state` 跟踪进度，失败设备保留旧通道并回滚。

**设备 SDK。** 提供 C/Java SDK 封装接入地址、凭证、主题、重连与离线缓存，暴露“上报属性 / 上报事件 / 响应控制”三个接口；厂商不必理解 ThingsBoard 协议，也避免各厂商各写一套重连与去重逻辑。

**接入治理。** 所有设备形态统一执行：

- 凭证：一机一密，禁用共享 Token；支持重置，重置后旧凭证立即失效并记审计。
- 命名：DeviceName 不超过 48 字符、仅英文数字下划线，导入时校验唯一性。
- 限流：在 HAProxy/Nginx 层按 IP 与设备限连接、限速率；社区版本身不限流，超限由入口层拒绝。
- 观测：连接数、上下行消息数、RPC 超时数、异常断开次数按设备与租户维度统计；异常接入写入日志，保留 7 天。
