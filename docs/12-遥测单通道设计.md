# 遥测单通道设计说明

> *中铁信科物联网平台文档集 ｜ 承载规范* ｜ [总目录](../README.md) ｜ 上一份 [11-前端联动开发指南](11-前端联动开发指南.md) ｜ 下一份 [13-物模型入湖链路](13-物模型入湖链路.md)

本文把“**属性与事件都走 ThingsBoard 的 Telemetry，只有少量特定数据使用 Attributes，不使用 Alarm**”这条决策写成可执行的规范：承载口径、白名单、事件契约、数据模型、迁移与验收。设计过程中的接入与物模型细节见《中铁信科物联网平台设计说明书》5.3–5.5、6.3 与 7.3。

## 1  决策摘要

- **一条上行通道**：设备所有业务数据（属性当前值、事件）都发到 `v1/devices/me/telemetry`，不区分“属性消息”与“事件消息”。
- **Attributes 是白名单制**：只保留 14 个键（元数据、配置、影子、OTA），新增必须走评审，避免属性表变成第二套遥测。
- **不用 Alarm**：平台不创建 ThingsBoard 告警实体，事件统一落 `plat_event`，由事件中心负责去重、收敛、通知与处置。
- **下行只走两个通道**：`rw` 属性与行为都走 RPC；配置类下发走共享属性（白名单内）。

## 2  为什么这样选

| 方案 | 属性承载 | 事件承载 | 主要问题 |
| --- | --- | --- | --- |
| A（常规做法） | Attributes | Alarm + Telemetry | 同一个键既在属性又在遥测，两套值容易不一致；告警生命周期与 TSL 事件语义不对应 |
| B（混合） | r→遥测、rw→属性 | alert/fault→Alarm、info→遥测 | 规则最复杂，前端要判断“这个键去哪查” |
| **C（本文）** | **全部遥测** | **全部遥测** | 需要自建事件表与事件中心；换来单一存储与单一查询口径 |

选 C 的三个理由：

1. **语义匹配**：TSL 的属性是“状态数据流”，事件是“带参数的瞬时事实”，两者天然是时序数据；ThingsBoard 的 Attributes 是“最新值覆盖”语义，Alarm 是“活动/确认/清除”工作流语义，都不如遥测贴近。
2. **查询统一**：最新值、历史曲线、事件时间线都从同一套键空间取数，聚合与看板不需要“属性 join 遥测”。
3. **跨租户可行**：告警在租户内产生，跨厂商汇总要再造一层；事件落平台库后按租户维度聚合是普通 SQL。

代价：ThingsBoard 自带的告警页与告警通知不能用了，运维必须在平台前端的事件中心工作；这一点在第 7 节说明补偿办法。

## 3  承载口径总表

| TSL / 业务元素 | 承载位置 | 说明 |
| --- | --- | --- |
| `profile.ProductId` / `CategoryId` / `version` | `plat_product`、`plat_product_tsl`；模板描述里放摘要 | 不进遥测 |
| `properties[].id`，`mode=r` | Telemetry 键 | 键名原样，不改写 |
| `properties[].id`，`mode=rw` | 上行 Telemetry + 下行 RPC `set` | 不再为每个 rw 建共享属性 |
| `name` / `desc` / `unit` / `min` / `max` / `step` | `plat_tsl_property` 目录 | 展示与校验用，不随报文传输 |
| `required` | 校验规则 | 规则链或 ingest 判定 |
| `events[]`（info / alert / fault） | Telemetry 保留键 | `event_id` / `event_type` / `event_ts` |
| `actions[].id` | RPC 方法名 | 参数与返回值按 TSL |
| 设备元数据（型号、绑定工点） | Server Attributes | 静态，低频 |
| 远程配置 | Shared Attributes `cfg_json` | 下发即覆盖 |
| 设备影子 | `shadow_desired`（shared）/ `shadow_reported`（client） | 只需当前值 |
| OTA | `fw_title` / `fw_version` / `fw_checksum` / `fw_size`（shared） | ThingsBoard OTA 约定 |
| 物模型校验依据 | Server Attributes `tsl_version` / `tsl_schema` | 规则链只读 |

## 4  Telemetry 规范

**上行主题**：`v1/devices/me/telemetry`，两种载荷都支持。

```
{ "ts": 1758000000000, "values": { "accX": 0.12, "rssi": -62 } }
{ "accX": 0.12, "rssi": -62 }
```

| 约束 | 规则 |
| --- | --- |
| 键名 | 等于 TSL 的 `id`，区分大小写；除事件保留键外不允许新造键 |
| 时间戳 | 毫秒；秒级需设备侧乘 1000；缺省由服务端补 |
| 类型 | bool / int / float / string / enum / timestamp；结构体先扁平化为 `父键.子键` |
| 批量 | 单条报文建议 ≤64KB，超大批量拆分；采样频率由 `cfg_json` 控制 |
| 频率 | 常规属性 30~300 秒；心跳单独用一个键（如 `hb`），用于离线判定 |

## 5  Attributes 白名单

属性只用于“低频、可覆盖、非时序”的状态。新增键必须同时满足：不需要历史、不需要聚合、变化频率低于每天一次。

| 键 | Scope | 写入方 | 读方 | 变更频率 |
| --- | --- | --- | --- | --- |
| `tsl_version` | server | 平台开通/发布任务 | 规则链、ingest | 版本发布时 |
| `tsl_schema` | server | 平台开通/发布任务 | 规则链 | 版本发布时 |
| `device_model` | server | 平台开通 | 前端、台账 | 一次 |
| `site_code` | server | 台账绑定任务 | 前端 | 改绑时 |
| `device_uuid` | server | 平台开通 | 规则链外发、ingest | 一次 |
| `tenant_id` | server | 平台开通 | 规则链外发、ingest | 一次 |
| `cfg_json` | shared | 平台或厂商 | 设备 | 配置变更时 |
| `shadow_desired` | shared | 平台/应用 | 设备 | 期望值变更时 |
| `shadow_reported` | client | 设备 | 平台/应用 | 状态变化时 |
| `fw_title` | shared | OTA 任务 | 设备 | 升级时 |
| `fw_version` | shared | OTA 任务 | 设备 | 升级时 |
| `fw_checksum` | shared | OTA 任务 | 设备 | 升级时 |
| `fw_size` | shared | OTA 任务 | 设备 | 升级时 |
| `server_time` | shared | 平台定时任务 | 设备 | 按需 |

反例（不要放属性）：设备当前温度、累计流量、告警次数、运行时长、电量——这些都要历史或聚合，属于遥测。

## 6  事件规范

**报文格式**：事件与属性同一条报文，靠三个保留键识别。

```
{ "ts": 1758000000000,
  "values": { "event_id": "over_speed", "event_type": "alert",
              "event_ts": 1758000000000, "speed": 92.5, "limit": 80 } }
```

| 保留键 | 含义 | 约束 |
| --- | --- | --- |
| `event_id` | 事件标识，对应 TSL `events[].id` | 必填，≤50，英文数字下划线 |
| `event_type` | `info` / `alert` / `fault` | 必填；与 TSL 定义不一致时以 TSL 为准并记校验异常 |
| `event_ts` | 事件发生时间（毫秒） | 可选，缺省用报文 `ts` |

**级别映射**：`info` 只入时间线；`alert` → MAJOR；`fault` → CRITICAL。

**幂等**：`(tenant_id, device_id, event_id, event_ts)` 唯一，重复上报只更新参数、不新增行。

**无“活动/清除”状态**：事件是已发生的事实。需要持续语义的由事件中心生成区间事件：

| 类型 | 开始 | 结束 |
| --- | --- | --- |
| 设备离线 | 最后心跳 + 超时阈值 | 心跳恢复 |
| 指标越限 | 指标连续 N 次越限 | 连续 M 次恢复 |
| 校验异常 | 连续失败 5 分钟 | 校验恢复 |

区间事件写 `start_ts` / `end_ts`，`end_ts` 为空表示仍在持续，查询“当前异常”即 `end_ts is null`。

**事件参数**：除三个保留键外的键都是参数，原样存 `params` JSON，不建列；需要检索的参数（如故障码）在 `plat_event` 里单独建索引字段。

## 7  不用 Alarm 的边界与补偿

| ThingsBoard 告警能力 | 平台替代 |
| --- | --- |
| 告警规则（模板阈值） | 事件中心规则：指标越限、心跳超时、校验失败 |
| 告警列表与详情 | 前端“事件中心”页面，按级别/产品/工点筛选 |
| 告警确认与清除 | 事件处置：确认（ack）、备注、关闭（close_reason） |
| 告警通知 | 事件中心通知：CRITICAL 即时通道，其余邮件/站内 |
| 告警统计 | `plat_event` 聚合，按租户/产品/工点出数 |

明确不做的事：不在 TB 里保留“活动告警”，不在模板里配 `alarms`，规则链不挂“创建告警”节点。模板 JSON 里的 `alarms` 字段是接口必填结构，留空数组即可。

## 8  数据模型与消息契约

**事件表**（PostgreSQL，随 `plat_*` 迁移）：

```sql
CREATE TABLE plat_event (
    id           BIGSERIAL PRIMARY KEY,
    tenant_id    UUID        NOT NULL,
    device_id    UUID        NOT NULL,
    product_id   VARCHAR(64) NOT NULL,
    event_id     VARCHAR(50) NOT NULL,
    event_type   VARCHAR(8)  NOT NULL CHECK (event_type IN ('info','alert','fault')),
    level        VARCHAR(8)  NOT NULL,               -- INFO/MAJOR/CRITICAL/WARNING/MINOR
    start_ts     TIMESTAMPTZ NOT NULL,
    end_ts       TIMESTAMPTZ,
    params       JSONB,
    status       VARCHAR(16) NOT NULL DEFAULT 'OPEN', -- OPEN/ACK/CLOSED
    ack_by       VARCHAR(64),
    ack_at       TIMESTAMPTZ,
    close_reason VARCHAR(128),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (device_id, event_id, start_ts)
);
CREATE INDEX idx_event_tenant_time ON plat_event (tenant_id, start_ts DESC);
CREATE INDEX idx_event_open ON plat_event (status, level) WHERE end_ts IS NULL;
```

**Kafka 契约**（规则链外发，ingest 消费）：

```json
{
  "v": 1,
  "tenantId": "b1f0…",
  "deviceId": "a7c2…",
  "deviceName": "WIFI_DIAG_0001",
  "productId": "9HYN9PJNOY",
  "tslVersion": "1.0",
  "ts": 1758000000000,
  "kind": "telemetry",
  "values": { "accX": 0.12, "rssi": -62 },
  "event": null,
  "invalid": []
}
```

事件消息同一结构，`kind="event"`，`event` 字段带 `{id,type,ts}`；校验失败时 `invalid` 列出错误，ingest 决定丢弃或降级。

## 9  查询与指标口径

| 需求 | 数据源 | 说明 |
| --- | --- | --- |
| 设备最新值 | TB 最新遥测或平台缓存 | 只读，不对 TDengine 发点查 |
| 历史曲线 | TDengine 明细/降采样 | 时间窗口限制单次 ≤7 天 |
| 事件时间线 | `plat_event` | 按设备/产品/工点过滤 |
| 当前异常 | `plat_event where end_ts is null` | 替代“活动告警” |
| 在线率 | 心跳遥测 `hb` + 超时阈值 | 不用连接事件 |
| 事件数指标 | `plat_event` 聚合 | 与 6.2 指标口径一致 |

禁止：业务系统直连 TDengine 或 TB 库；前端自行解析 TSL 原文。

## 10  迁移与灰度

1. 建 `plat_event` 与索引；ingest 先只写事件、不改查询。
2. 规则链去掉创建告警节点，改为外发 Kafka；事件字段缺失时按 `info` 兜底。
3. 清空设备模板的告警配置（`alarms: []`），避免残留告警继续产生。
4. 存量活动告警一次性导出为 `plat_event` 历史记录（`status=CLOSED`，备注“迁移归档”）。
5. 事件中心上线后，通知从 TB 告警切到事件中心；旧告警页保留只读两周。
6. 观察两周：事件量、误报率、通知到达率达标后，关闭旧告警入口。

## 11  验收清单

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 发属性遥测 | TB 最新值可见，TDengine 有明细 |
| 2 | 发 `event_type=alert` | `plat_event` 新增一条，level=MAJOR |
| 3 | 重复发同一 `event_ts` | 不新增行，只更新参数 |
| 4 | 发 `event_type=fault` | level=CRITICAL，触发即时通知 |
| 5 | 断开设备超过 3 个心跳周期 | 生成区间事件，`end_ts` 为空 |
| 6 | 设备恢复心跳 | 区间事件补 `end_ts`，状态可关闭 |
| 7 | 发未定义键 | 按 `strictUnknown` 策略处理，不入事件表 |
| 8 | 检查 TB 告警页 | 无新增告警；模板 `alarms` 为空 |
| 9 | 查属性列表 | 只有白名单 14 个键 |
| 10 | `rw` 属性下发 | 走 RPC `set`，设备回执，遥测确认新值 |

## 12  已知限制

- **告警页不可用**：TB 原生告警 UI 与运维习惯不同，需培训与前端补偿。
- **事件风暴**：设备故障时可能每秒上报同一事件，靠幂等键与 5 分钟窗口合并；仍建议设备侧做 1 秒最小间隔。
- **属性白名单维护**：新增属性键要走评审，否则会退化成“用属性存遥测”。
- **跨租户事件聚合**：事件在 `plat_event` 里带 `tenant_id`，超管可全量查，厂商账号必须强制过滤，避免越权。
- **ThingsBoard 版本差异**：不同版本的属性 scope 与 RPC 主题细节略有差异，升级时按第 11 节回归。
