# Chromium credits

`CREDITS.txt` lists the third-party software in the Chromium builds that the web-report packages bundle (see
`../chromium.js`), with its license texts. It is what Chromium shows on its page about:credits. The third-party notices
take it as the license file of the chromium components, through `[license_files]` in `tools/src/main/notices/policy.toml`:

- the notices of the Linux packages get the Linux credits;
- those of the Windows package get the Windows credits;
- the combined CI check (`target/THIRD-PARTY-NOTICES`) gets the whole file.

The Linux and Windows builds have nearly the same entries: in 156.0.8078.0, all but 9. Those of one build are in a
section at the end of the file, under a line `======== Only in the <platform> build ========`, which the notices of the
other platform leave out.

## Why we keep the credits

The snapshot builds that the packages bundle embed only a placeholder about:credits. Chromium generates the real page
only in official builds (`generate_about_credits` defaults to `is_official_build`), and the snapshot builders do not
make official builds.

## Where the texts come from

Chromium makes the page with `tools/licenses/licenses.py credits`. It does not read the build graph: it lists every
`third_party` directory of the checkout whose metadata says `Shipped: yes`. So the page depends only on the commit and
on which platform's dependencies the checkout has, not on the build arguments. An official build of the same code has
the same page.

Chrome for Testing is such an official build, and its `resources.pak` holds the page. For 156.0.8078.0, we generated
both pages from the Chromium source at the exact commits of the snapshots: Chrome for Testing 156.0.8078.3 has the same
pages, byte for byte (494 entries for Linux, 489 for Windows). It is built a few commits later, on the release branch,
so its page could differ only if a third-party directory was added or removed in those commits.

Two other sources are not right for these builds. The Chromium package of Debian takes 37 libraries from other Debian
packages, so its credits leave them out. `licenses.py license_file` lists the same components, but without merging the
duplicate entries the page merges.

## Why the conversion to text loses nothing

The page is a template filled once per entry with three fields (the name, the homepage address and the license text),
each passed through Python's `html.escape()`, which only replaces `&`, `<`, `>`, `"` and `'` with entities. Taking the
fields back and undoing those replacements gives the texts exactly. As a check, the fields, escaped and filled into the
template again, must give back the page byte for byte. For 156.0.8078.0 they do.

## Updating

When `../chromium.js` moves to another Chromium version:

1. Take the earliest Chrome for Testing version of that release, and the `resources.pak` of its Linux and Windows
   builds.
2. Get the credits page out of each: it is the resource that starts with `<!-- Generated by licenses.py`.
3. Convert both pages to `CREDITS.txt` as above, with the check, keeping the layout of the current file: the entries of
   both builds in the page's order, then the section of each build's own entries.
4. Change the version in the two chromium entries under `[license_files]` in `tools/src/main/notices/policy.toml`. Until then, the
   notices stop.
5. Run the third-party notices check (see `docs/licensing-guide.md#checking-the-notices-locally`).

## From the Chromium source

To be exact, or if Chrome for Testing is not available, generate the pages as the build would, without building
Chromium:

1. Find the commit of each snapshot: `got_revision` in the `REVISIONS` file of its directory.
2. Make a shallow checkout of that commit, without hooks, with only the dependencies of its platform. Dependencies of
   another platform left on disk change the page.
3. Run `licenses.py credits` with `--target-os` of the platform, as `//components/resources:about_credits` does.

This takes about 31 GB of disk and a few hours. Work in a throwaway container and directory. To move a shallow checkout
to another commit, fetch that commit shallowly first: `gclient sync --revision` would download the whole history. The
Windows page can be generated on Linux: the page needs no Windows toolchain, only the Windows dependencies.
